## 4. Agent 模式与长期硬约束

Agent 三种模式：
- Google / Native
- COMPAT
- Auto

长期要求：
- 手动 Native 必须真正强制 Native，供 A/B。
- COMPAT 允许官方未声明工具调用支持的模型参与测试。
- 不设通用“最多 8 次工具调用”上限。
- 重复相同 COMPAT tool call 允许；用户可以使用现有 Stop 按钮终止循环。
- 泛用模型 <2B 默认不进入 Agent；FunctionGemma 等专用函数模型可例外。
- `.litertlm` context <4096 实测对 Agent 不可靠，4096 作为实践下限。
- 当前优先非 thinking 模型或 thinking 能可靠硬关闭的模型。

Qwen3.5 COMPAT 工具调用格式已在 parser 中适配：
`<tool_call><function=name><parameter=key>value</parameter>...</function></tool_call>`

Thinking hard-off：
- extraContext：`enable_thinking=false`
- `preserve_thinking=false`
- `thinking_token_budget=0`
- Native：`ThinkingConfig(enableThinking=false, thinkingTokenBudget=0)`

## 5. Agent 性能阶段已经得到的结论

MCP210 稳定参考：
- TTFT avg ~13.55s
- continuation ~12.98s
- total ~41.26s
- hidden thought 0

MCP211 native benchmark：
- TTFT ~12.2s
- prefill 占 native TTFT ~98.6%

- first turn ~13.54s
- search tool ~5.19s

核心判断：
- 工具执行本身并非主要延迟来源。

- MCP212 第二个 warm Conversation 曾在 heap ~5826MB 崩溃；没有 native cached-session 级别修复前不要重走该路线。
- MCP212 的后台 warm Conversation 方案应视为失败实验。

## 10. MCP238 下载器实现

主要 patch：
- `Android/src/scripts/patch_mcp238_qwen35_model_download.py`
- `Android/src/scripts/patch_mcp238_qwen35_model_download_v3.py`

v3 的职责：
- 把旧 base patch 的 4-part metadata 动态替换为最终 10-part metadata。
- 替换完整模型 SHA 为 `d5e975...`。
- part sizes = `[480_000_000] * 9 + [460_966_112]`。
- 保留 fail-fast anchor；metadata 不匹配时构建直接失败。

base patch 的功能：
1. 同时更新：
   - 根目录 `model_allowlists/1_0_14.json`
   - `Android/src/app/src/main/assets/model_allowlists/1_0_14.json`
2. 完全删除：
   - `Qwen3.5-2B LiteRT-LM Q8 experimental`
   - `Qwen3.5-2B LiteRT-LM Q4 experimental`
   - `paulsp94/Qwen3.5-2B-LiteRT-LM` 的 `qwen35_2b.litertlm`
   - `paulsp94/Qwen3.5-2B-LiteRT-LM` 的 `qwen35_2b_q4.litertlm`
3. 增加唯一新模型：
   - `Qwen3.5-2B LiteRT-LM Q8 4096 Plaza`
   - 4096 context
   - maxTokens 1536
   - accelerators `gpu,cpu`
   - taskTypes：llm_chat / llm_prompt_lab / llm_agent_chat
   - bestForTaskTypes：llm_agent_chat
4. `DownloadRepository.kt` 只对该模型注入 multipart metadata。
5. `DownloadWorker.kt` 增加 multipart 顺序恢复：
   - 单一 partial final file
   - 识别已完成 part
   - 每 part 支持 Range resume
   - CDN 忽略 Range 返回 200 时，截断回该 part 起点重新写，避免重复字节
   - 每 part 校验累计边界
   - 全部下载后校验总长度
   - 对最终 partial file 计算 SHA-256
   - SHA mismatch 时删除 partial 并报错
   - 校验成功后 rename 为最终 `.litertlm`
6. 正常其他模型继续走原单文件/备用镜像下载逻辑。

这一实现避免了“10 个 part 全部落盘 + 再复制成 4.78GB final”的双倍空间路线；最终模型直接持续 append 到单一 partial 文件。

## 14. 真机失败时的判断树

### 下载阶段失败
先看：
- 当前 part index
- local partial size
- HTTP 200 / 206
- 是否 CDN 忽略 Range
- part 累计边界
- final size
- SHA mismatch

如果下载失败，不要先动 LiteRT-LM runtime。

### final SHA mismatch
- 保留日志。
- 先核对 Release part inventory 是否变化。
- 核对 part 顺序。
- 核对恢复后是否出现重复字节。
- 不要用“忽略 checksum”作为修复。

### Engine.initialize magic 失败
如果新 Plaza 模型仍出现 `Invalid magic number`：
- 这是 container 层问题。
- 获取新模型前 8 bytes、完整 SHA 和实际 size。
- 与 Release 权威值核对。
- 不要 naive 改 header。

### KV/cache contract 失败
例如 `No KV cache inputs found`：
- 表明容器已走更深。
- 优先调查新 exporter、executor metadata、LiteRT-LM 0.15 runtime contract。
- 此时才评估 runtime A/B。

### Conversation 成功但 Agent 工具失败
进入 parser / tool adapter 层：
- COMPAT format
- thinking tags
- tool result continuation
- Native/COMPAT mode routing
- explicit search enforcement

当前 LiteRT-LM 0.15.0 已形成稳定产品基线。

LiteRT-LM runtime 升级以后需要独立 A/B；不要在同一 MCP 版本同时修改：
- runtime
- 模型 package
- parser
- conversation reuse
- tool protocol

性能实验一次只改一个主要变量。

26B 模型排障长期顺序：
Load Probe -> Chat -> Agent。

外部导入模型历史默认 32K context + CPU first 曾被认为是大型模型加载问题的重要嫌疑。需要实验时单独控制变量。
